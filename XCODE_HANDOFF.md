# Tape for iOS: Xcode handoff

For the agent (or person) doing the first real build. Written 2026-09-19 after the Kimi K3
adversarial review was applied. Read this top to bottom before opening Xcode; it is short.

## What you are receiving

- `Tape-iOS/`: a SwiftPM package (`TapeCore`, Foundation only) plus a SwiftUI app target
  (`App/Tape`) described by `project.yml` for XcodeGen.
- `TapeCore` **builds and its 30 tests pass** on Linux (Swift 5.10.1) with
  `-strict-concurrency=complete` and no warnings. Expect the same on macOS with Xcode 15.4
  or 16.
- The app target **has never been compiled with a real SDK.** It was type-checked on Linux
  against a stand-in SwiftUI/Charts module with iOS 17 signatures, which found and fixed
  four real defects, but a stub is not the SDK. Budget for a small number of compiler
  complaints on the first build; the logic should not need to change.
- `REVIEW_NOTES.md`: finding-by-finding disposition of the review, what was verified and how.
- `README.md`: layout, requirements, budget model, first-run behaviour.

## Step 1: generate the project

```
cd Tape-iOS
brew install xcodegen      # once
xcodegen generate
open Tape.xcodeproj
```

Then set the team and change `PRODUCT_BUNDLE_IDENTIFIER` (`com.example.tape` is a
placeholder) in `project.yml` and regenerate, or edit it in the target settings.

Everything the target needs is in the folder: sources, the local `TapeCore` package, the
test target, and an asset catalog with an empty `AppIcon` slot (drop a 1024×1024 PNG in
`App/Tape/Assets.xcassets/AppIcon.appiconset` and add it to `Contents.json`, or use
Xcode's asset editor). `Info.plist` is generated by XcodeGen from the `info:` block in
`project.yml`; there is no checked-in plist. No signing entitlements, no ATS exceptions,
no third-party packages, nothing to fetch from the network at build time.

If XcodeGen is not an option, README "Option B" lists the manual steps (new iOS App,
drop `App/Tape` in, add the local package, deployment target 17.0).

### If Xcode says "Missing package product 'TapeCore'"

The package reference is almost certainly fine; the Xcode *session* is stale. Seen
2026-09-19: the project built from the command line while the open Xcode window kept
failing, and closing and reopening `Tape.xcodeproj` fixed it with no file changes. Do not
remove and re-add the package in Package Dependencies; that makes the project drift from
`project.yml`, and the next `xcodegen generate` overwrites it anyway.

1. Check the truth on disk first:
   `xcodebuild -resolvePackageDependencies -project Tape.xcodeproj -scheme Tape`
   should print `TapeCore: <this folder>`.
2. Make sure this folder is not also open in Xcode as a bare package (opening the folder
   or `Package.swift` directly does that). A package can only be loaded by one window.
3. Close and reopen `Tape.xcodeproj`, or File > Packages > Reset Package Caches.
4. Quit Xcode before running `xcodegen generate`. Regenerating underneath an open window
   is one way to get into this state. `project.yml` is the source of truth; settings
   edited in the Xcode UI (a 17.6 deployment target crept in this way) are lost on the
   next generate, so change them in `project.yml`.

## Step 2: run the package tests first

```
swift test                 # from Tape-iOS/, on the Mac
```

or select the `TapeCoreTests` target in Xcode and press ⌘U. All 30 must pass before you
touch the app target; if one fails on macOS but passed on Linux, it is almost certainly a
Foundation difference (formatting, time zones) and worth reporting rather than patching.

## Step 3: build the app target and read the diagnostics

Things most likely to need a touch, in order of likelihood:

1. **SwiftUI signature drift.** The stub matched iOS 17 signatures for every API in use.
   Candidates if something does not compile: `.sensoryFeedback(_:trigger:condition:)`
   (DetailView), `.onChange(of:) { old, new in }` two-parameter form (iOS 17+),
   `ToolbarItem(placement: .topBarTrailing)` (iOS 17+), `ChartProxy.plotFrame` (iOS 17+),
   `.confirmationDialog(_:isPresented:titleVisibility:actions:message:)`. All exist in the
   iOS 17 SDK; if the deployment target is set lower they will fail.
2. **Strict concurrency warnings** (`SWIFT_STRICT_CONCURRENCY = complete` in `project.yml`).
   Every `View` struct that reads the model is marked `@MainActor`; `AppModel` is
   `@MainActor @Observable`; the two network types are actors. If Xcode 16 flags something
   the stub did not (a `Sendable` inference on a closure, say), prefer adding an explicit
   `@MainActor` or `@Sendable` to the site over turning the setting down.
3. **`Locale.current.region`** in `AppModel.boot()` (iOS 16+) is fine at 17.0.
4. **`Store: @unchecked Sendable`** wraps `UserDefaults`; on Apple SDKs `UserDefaults` is
   already `Sendable`, so the annotation is harmless either way.
5. **List row layout.** `InstrumentRow` uses fixed 104/112 pt columns plus a sparkline that
   takes the remainder. On a 320 pt-wide device (iPhone SE) the sparkline gets ~60 pt; if it
   looks cramped, drop the sparkline below 360 pt width. Not a compile issue.

Anything else that appears is a bug in this handoff; please note it in the review notes
rather than silently working around it.

## Step 4: first-run checks on a simulator (no key needed)

1. Launch. Expect: empty tape, the key sheet open with "Not now", status chip `NO KEY`.
2. Tap "Not now". Expect: sheet closes, a "No data key yet" banner above the search field,
   six starter chips (SPY, QQQ, AAPL, NVDA, BTC/USD, XAU/USD).
3. Tap a chip. Expect: the row appears with "…" and the key sheet opens (no fetch without
   a key). Tap "Not now" again.
4. Type `gold` in search. Expect within a frame, with no network: GLD, XAU/USD and
   PAXG/USD at the top (ETF, commodity, crypto), then the other curated gold names (IAU,
   GDX, GS). With a key, GOLD (the NYSE stock) joins at the top after 300 ms. Type `zzq`:
   expect the "Track "ZZQ" anyway · unverified" row.
5. Tap the status chip. Expect the explainer sheet.
6. Settings → Display: switch to red-up. Expect ▲ glyphs turn red, ▼ green, the choice
   persists across relaunch. Settings also states dark-only.

## Step 5: checks with a real Twelve Data key (free Basic plan)

Costs about 10 credits. Watch the Settings "Used today" line against the Twelve Data
dashboard; they should agree within one or two credits (the app counts locally).

1. Paste the key. Expect a 1-credit `SPY` probe, then "Connected to Twelve Data." A wrong
   key must keep the sheet open with Twelve Data's message and the chip `KEY REJECTED`;
   no polling loop, no repeated toasts.
2. Add SPY and BTC/USD. Expect one 2-credit batch and one chart credit; footer says "every
   3 minutes while US markets are open and every 21 minutes overnight for the 24-hour rows"
   (numbers scale with the book size).
3. Pull to refresh. Expect a batch immediately (user-initiated, may spend the reserve).
4. Swipe a row left → Remove → "Undo" on the toast restores it in place.
5. Background the app for a minute and return. Expect no fetch unless the cache is older
   than the poll interval.
6. Outside US hours with only equities on the tape: the chip reads `CLOSED · HH:mm`, the
   footer names the next session, and no batches fire until 09:31 ET.

## Deliberately not done (do not "fix" these as bugs)

- No fabricated demo prices; the cold open shows chips and a banner instead.
- No query-parameter auth fallback on iOS (the web build keeps a session-only one).
- No background fetch, no WebSocket, no `/api_usage` calls.
- Dark-only, fixed fonts (Dynamic Type is a v1.1 item), en_US formatting, no
  `AXChartDescriptor` audio graph yet, no holiday table (a holiday costs one batch).
- `AppModel` has no unit tests; the web harness covers the equivalent logic. Adding a
  `Transport` fake through `AppModel.init` is the intended next step.

  Views/WatchlistView    list, banner, chips, sparkline, status chip + explainer sheet

  Views/SearchBar        dropdown with the unverified "track anyway" row
